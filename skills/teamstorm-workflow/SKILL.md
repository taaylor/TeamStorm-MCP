# Карта выполнения задачи TeamStorm

Это шаблон контракта версии 1 для MCP и демона. Он отключён по умолчанию.
Не сообщай об успешном планировании без подтверждения от MCP.

## Настройка

Замени примеры `external_status` точными значениями статусов своего проекта.
Здесь используются названия; если API требует идентификаторы, укажи их строками.
Настрой переходы и критерии готовности. Поле `id` идентифицирует карту,
`revision` увеличивай при изменении правил. `schema_version` — версия формата.

Храни карту в проекте и задай обоим процессам одинаковый абсолютный путь
`TEAMSTORM_WORKFLOW_PATH` к этому файлу и общий `TEAMSTORM_QUEUE_PATH` к SQLite.
После изменения карты перезапусти оба процесса.
В пользовательском скилле Codex или Claude Code укажи путь к нему и поручение
следовать карте. Само размещение файла не подключает его к клиенту или серверу.
Прочитай активную карту инструментом `teamstorm_get_workflow`.

## Машиночитаемая карта

Единственный блок `yaml` ниже — источник правил загрузчика LangGraph.
Не извлекай исполняемые правила из свободного текста и не генерируй из него код.
Один файл описывает одну карту; выбор карты для проекта должен быть однозначным.

```yaml
schema_version: 1
id: teamstorm-default
revision: 1
timezone: Asia/Yekaterinburg

states:
  backlog:
    external_status: "Backlog"
  in_progress:
    external_status: "In Progress"
  review:
    external_status: "Review"
  ready:
    external_status: "Ready"
  done:
    external_status: "Done"

transitions:
  - from: backlog
    to: in_progress
    actor: mcp
  - from: in_progress
    to: review
    actor: mcp
  - from: review
    to: in_progress
    actor: mcp
  - from: review
    to: ready
    actor: mcp
  - from: ready
    to: in_progress
    actor: mcp
  - from: ready
    to: done
    actor: daemon

scheduled_finalization:
  trigger_state: ready
  final_state: done
  deadline_source: user_prompt
  discovery_scope: all_accessible_tasks
  missing_deadline: skip
  trigger_left: cancel_queue_keep_intent
  overdue: finalize_when_trigger_reached
```

Пример маршрута: Backlog → In Progress → Review → Ready → Done.
Из Review и Ready разрешён возврат в In Progress. Последний переход делает демон.
Это описание YAML-карты, а не второй источник правил.

## Правила формата и переходов

- Ключи состояний — внутренние идентификаторы; `external_status` — значения API.
  Значения должны быть уникальны и существовать в соответствующем проекте.
- Разрешены только перечисленные направленные переходы. `actor` принимает
  `mcp` или `daemon`; это исполнитель операции, а не поле, которому можно
  доверять без проверки на стороне сервера.
- `trigger_state` и `final_state` должны ссылаться на разные существующие
  состояния. Единственный переход демона — между ними; из финального состояния
  нет исходящих переходов. MCP не выполняет переход демона.
- Неизвестная версия, поле, значение политики, состояние или неоднозначная
  карта — ошибка конфигурации. При ошибке не выполняй автоматические изменения.
- Перед каждой записью получай актуальный статус и проверяй разрешённое ребро.
  При конфликте обнови контекст, не перезаписывай чужое изменение вслепую.
- Повтор запроса в уже достигнутый статус не должен создавать новую операцию.
  После неоднозначного результата записи сначала проверь фактический статус.
- Свяжи сохранённое расписание с `id` и `revision` карты. При несовпадении
  ревизии приостанови автоматическое закрытие до явного обновления расписания.

## Действия ассистента через MCP

1. Прочитай задачу, активную карту и доступные инструменты. Пользовательское
   поручение выполнять флоу даёт контекст для переходов; наличие скилла само
   по себе не разрешает изменять задачи. Согласуй его с основным скиллом TeamStorm.
2. Из «приступай к задаче и закрой её к 18:00» выдели время закрытия. Привяжи его
   к дате и часовому поясу пользователя, при отсутствии пояса используй `timezone`.
   Сохраняй `close_at` как ISO 8601 с UTC-offset. Если дата неоднозначна или
   указанное время уже прошло, уточни намерение, не переноси молча на завтра.
3. Если время задано, сразу вызови `teamstorm_schedule_task_closure` с задачей,
   `close_at` и финальным `external_status` в `target_status`. Сервер привяжет карту.
   До Ready запись имеет состояние `waiting`, очередь ещё не активна. Так расписание
   переживёт завершение сессии до достижения Ready.
4. Следуй разрешённым переходам. В этом примере переходи в Review после
   реализации и проверок; в Ready — после завершения требуемого ревью и
   устранения замечаний. Адаптируй эти критерии под проект. Дедлайн сам по себе
   не означает готовность и не разрешает пропускать этапы.
5. При обнаружении Ready демон активирует очередь закрытия. Сообщи пользователю
   фактически сохранённое время и статус; не обещай, что работа обязательно
   завершится к этому времени. Демон закрывает готовую задачу не раньше `close_at`.

Если время в промпте отсутствует, не создавай и не меняй расписание: существующий
срок сохраняется, без него автоматического закрытия нет. Если пользователь явно
просит закрыть по времени, но не сообщает срок, уточни его. Промежуточный флоу
можно выполнять без срока. Расписание читается через `teamstorm_get_task_closure`,
отменяется через `teamstorm_cancel_task_closure`.

Изменение содержимого карты, её id или revision приостанавливает старое расписание
(`suspended`); после согласования новых правил явно сохрани расписание заново.

## Правила демона

На каждом цикле просматривай весь доступный через API список задач с пагинацией,
чтобы обнаруживать и ручные переходы. Обрабатывай только задачи, для которых
однозначно выбрана эта карта. Частичный сбой чтения не означает удаление задачи.

| Ситуация | Действие |
| --- | --- |
| Есть намерение, задача ещё не в Ready | Не создавать активную очередь |
| Ready наступил раньше `close_at` | Создать очередь, ждать времени |
| Ready наступил после `close_at` | Создать очередь и закрыть при ближайшей успешной проверке |
| Ready достигнут вручную | Применить те же правила при наличии намерения |
| Нет сохранённого времени | Пропустить автоматическое закрытие |
| Задача вышла из Ready | Отменить очередь, сохранить намерение; при возврате активировать заново |
| Задача уже в Done | Завершить расписание без повторной записи статуса |
| Ошибка API или неизвестный статус | Не менять статус, повторить проверку позже |

Непосредственно перед финальным переходом перечитай задачу и расписание:
статус должен быть Ready, время наступило, намерение не отменено, ревизии совпадают.
Защищай запись от конкурентного изменения средствами API, если они доступны;
одного предварительного чтения недостаточно для атомарной гарантии.
Не заявляй такую гарантию, если API её не поддерживает.
Текущая реализация перечитывает данные, но GET и PATCH не атомарны. Запускай один
демон на общую очередь; конкурентное изменение после последней проверки возможно.

Храни намерения и очередь устойчиво к перезапуску. Повторное обнаружение задачи
не создаёт дубликат. Изменение времени обновляет ревизию расписания и делает
устаревшую работу демона недействительной; отмена деактивирует и намерение, и очередь.
Демон не интерпретирует промпты, не выполняет промежуточные этапы и не оценивает
качество работы: статус Ready является сигналом завершения требуемых проверок.
